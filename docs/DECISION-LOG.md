## 2. Key Architectural Decisions and Evidence Records (`D-001` to `D-014`)

### `D-001`: Party vs ProjectCustomer Separation & Resolution
- **Decision:** The organization-wide `parties` table is the canonical source of counterparty identity (`id`, `party_kind`, `display_name`, `normalized_display_name`). Project-scoped `project_customers` retain relationship-specific contact, status, source, document data, and their own UUID. Migration #12 retired the duplicated identity mirrors. Migration #13 enforces the project-scoped normalized Party-name/phone uniqueness rule using deferred PostgreSQL triggers and transaction-scoped advisory locks, covering relationship writes and Party identity changes. Its preflight must stop on pre-existing duplicates; no automatic deletion or merge is allowed. Fuzzy auto-merging remains rejected in favor of human-approved manual Party merge workflows.

### `D-002`: Password Hashing Policy
- **Decision:** PROMO GEST uses **`Pbkdf2PasswordHasher`** (`PBKDF2-SHA512`, 310,000 iterations, 16-byte random salt, serialized format `PBKDF2-SHA512$<iterations>$<salt>$<hash>`). Any future algorithm migration requires an explicit independent ADR ensuring backwards compatibility and transparent rehashing upon successful login.

### `D-003`: Module K Document Management Two-Stage Split (`K-Min` vs `K-Full`)
- **Decision:** To resolve roadmap/catalog discrepancies, Module K is split into **`K-Min`** (local file upload/download with SHA-256 verification, required before Phase 2 Contracts) and **`K-Full`** (enterprise-wide archiving, legal hold, retention policies, scheduled in Phase 5).

### `D-006`: Do Not Store API or Health Responses in HTTP Caches (PR #48 / Run #539)
- **Decision:** `SecurityHeadersMiddleware` assigns `Cache-Control: no-store` to every request whose path belongs to `/api` or `/health`, case-insensitively. The rule applies centrally so it does not depend on individual frontend calls remembering to set Fetch `cache: 'no-store'`.
- **Boundary:** Static SPA routes (`/`, `/index.html`), hashed `/assets/*`, and `/manifest.webmanifest` are excluded. Existing Service Worker rules still bypass API and health requests; they are a separate protection layer and are not changed by this decision.
- **Rationale:** Authenticated API responses may contain session, customer, project, or operational data. A Service Worker bypass does not control the browser's ordinary HTTP cache, and selective frontend fetch options do not reliably cover all API calls.
- **Regression coverage:** `SecurityHeadersMiddlewareTests.cs` covers API/health paths including unknown endpoints, uppercase prefixes, static shell/assets, and near-miss routes (`/apiary`, `/healthcare`). The policy does not alter cookies, CSRF, permissions, persistence, database schema, migrations, or cloud/local deployment boundaries.
- **Verification:** PR #48 (`73b3afbe748619c73489dc6f7f736a70d3607567`) passed all three PR CI jobs in Run #538 (`43763596953`). Squash merge `23f019de7c787c0f93b5b7f0b5cec69992ff087a` was verified by post-merge Run #539 (`43763807711`), with all three jobs successful.

### `D-012`: Phase 1 Party & Employee Master-Data Scope Fence (16 November 2026)
- **Decision:** Phase 1 retains the verified core only: canonical organization-wide `Party` identity (`Person|LegalEntity`, display name and normalized name); the existing project-scoped `ProjectCustomer` compatibility relationship; and `User` as the authentication/authorization account. `ProjectCustomer` continues to own its current project-specific phone, email, address, contact person, preferred language, commercial source/status, identity-document reference and interaction history. `ProjectMember` remains an access-control relationship, not an employment record.
- **Deferred from Phase 1 — `PartyContactPoint`:** Do not move or duplicate existing contact values into Party now. Keep project-specific contacts on `ProjectCustomer`. Revisit shared Party contact points only with a proven cross-project use case and a written ownership/verification/provenance/effective-date/project-override policy. Phone and email values are not globally unique identity proofs.
- **Deferred from Phase 1 — `PartyIdentifier`:** Do not introduce NIN/CNI/NIF/NIS/RC or other sensitive identifiers in this slice. Before implementation require a documented lawful purpose and qualified Algerian practitioner review, field-level protection/key lifecycle compatible with local-first hosting, masking, dedicated read/write permissions, redaction from logs/audit/search/errors, retention/correction rules, restore/key-recovery evidence, and PostgreSQL uniqueness/concurrency tests appropriate to issuer and jurisdiction.
- **Deferred from Phase 1 — `PartyRepresentative`:** Keep representative/mandate modelling out until the legal contract domain defines the represented party, relationship type, effective period/status, authority evidence and permitted acts, with qualified Algerian legal/notarial review. Existing free-text `ContactPerson` remains a legacy project-level field; this decision does not reinterpret it as legal authority.
- **Deferred from Phase 1 — human-reviewed Party merge (`PartyMergeRecord`):** Do not merge Parties in this phase. A later merge workflow must show a complete impact preview, select a survivor explicitly, preserve all former IDs and references (including ProjectCustomer, interactions, reservations, documents and audit history), define conflict resolution per field, and provide append-only audit plus a rehearsed recovery/undo strategy. Similar names or shared phones remain review signals only; automatic merge is prohibited.
- **Deferred from Phase 1 — generic `ProjectPartyRole`:** Do not relabel `ProjectCustomer` as a generic role or replace its stable UUID. Keep customer/prospect workflows on their current compatibility model. Add role/lifecycle-aware project relationships only when the later supplier, contractor, consultant or legal workflows require them, with multiple-role/history semantics and explicit project membership/capability enforcement.
- **Deferred from Phase 1 — `Employee`:** No Employee table, HR profile migration or new HR permissions in this phase. Any future Employee is organization-owned and linked to a natural-person Party; its User link is optional and separately constrained. An employee may have no login, and a technical User may have no Employee. User credentials, sessions, security stamp, role assignments and account lifecycle remain owned by `User`; never bulk-convert users into employees or derive HR roles from `UserRole`/`ProjectMember`.
- **Compatibility note:** Existing `CreateEmployeeRequest` / `UpdateEmployeeRequest` contract names and `UserManagementService.CreateEmployeeAsync` / `UpdateEmployeeAsync` methods currently manage `User` login accounts, not an Employee entity. Do not infer physical Employee support from those names; renaming the legacy API/DTO surface is outside this decision.
- **Security and data boundary:** No Party search permission grants access to project contacts, identity documents, reservations, or interactions. Preserve `parties.directory.read`, `parties.identity.manage`, `customers.read`, `customers.manage`, explicit `ProjectMember` checks, category capabilities, CSRF, audit and concurrency unchanged. No automatic Party merge, automatic Party↔User association, contact synchronization, schema migration, runtime endpoint, seed permission, production database or Cloud SQL mutation is authorized by this scope decision.
- **Exit criteria for future slices:** Each deferred capability needs its own business outcome, source/legal basis, data owner, lifecycle and history model, separate permissions/PII matrix, append-only audit semantics, concurrency and uniqueness rules, additive migration/preflight/rollback plan, PostgreSQL 18 integration/restore coverage, API/UI traceability and Arabic RTL/French LTR acceptance where UI changes. `REQ-D05` and `REQ-D06` remain `PLANNED`; Module D remains `PARTIALLY_IMPLEMENTED`.
- **Implementation status:** This is a documentation scope decision only. It does not claim any deferred capability is implemented or change the current database/runtime baseline.

Separate technical administration from ordinary daily work. This is a design approval only; it does not claim any of these missing UI capabilities has been implemented.
- **Source-audited current state:** The current SPA has only in-memory routes `overview`, `projects`, `users`, `audit`, and `organization`; no route-addressable project context, switcher, persistent project identity strip, or recent/favorite view exists. ### D-014: Project Estimated Budget Financial Capability Boundary (17 November 2026)
- **Decision:** Classify Project.EstimatedBudgetDzd as restricted project financial data. Read requires an explicit ProjectMember.CanViewFinancials == true membership on the target project. Updating the amount additionally requires projects.manage and ProjectManager membership. No implicit bypass exists for SYSTEM_ADMIN or ProjectManager.
- **Non-financial update rule:** A Project Manager without the financial capability may update other master data by sending EstimatedBudgetDzd: null; the API preserves the stored amount. Any numeric amount attempt without the capability is rejected and audited as ACCESS_DENIED.
- **Creation rule:** Existing non-administrator project creation continues to grant the creator the existing explicit Project Manager capabilities, including CanViewFinancials. A System Administrator with no project membership may create only a zero estimate; a non-zero estimate requires a financial-authorized member.
- **Contract/UI/preview:** DTO budget values are nullable and redacted to null unless the actor has the capability. React hides the editor and displays a dash; Vite-only preview mirrors the API. Successful financial list/detail reads use PROJECT_FINANCIALS_VIEWED.
- **Implementation and verification boundary:** Merged in PR #80 at `61bcf8b0a0b2e3967fa5b7add904afd9bc1b0da3` (final head `4a160c164db12ba01cb83a4f857d1b8d8fc0c921`). Remove switch-project actions from the active-project sidebar heading and the project identity strip. The identity strip continues to display project code, localized name, location and status, plus the independent pin/unpin and Project Directory actions.
- **Project section navigation:** The active-project sidebar is the single navigation surface for project sections. Remove the duplicate horizontal project tab bar from the project page. Keep route-addressable project sections, the section PageHeader and breadcrumb, and the sidebar's existing module-state labels.
- **Safety invariants:** This is a presentation/navigation consolidation only.
