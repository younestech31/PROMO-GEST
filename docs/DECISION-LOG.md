### ADR-0012 — Temporary Employee Password Rotation After Creation or Administrative Reset (20 November 2026)

- **Context:** Employee creation and administrator password reset currently accept a password known to the account manager. Reset already rotates `SecurityStamp` and revokes active sessions, but it does not force the employee to replace the credential before business access.
- **Decision:** The local administrator who has `users.manage` supplies a temporary password through the existing create/reset workflow. It is valid for 24 hours. The ERP does not send it by e-mail/SMS or any cloud service; it is handed over through the organization's approved local channel. Only the existing password hash is persisted; neither the plaintext temporary value nor a derivative is included in audit summaries.

Server middleware allows only own-session status, CSRF token acquisition, health probes, SPA shell GET, password change, and logout. All organization/project/party/customer/user/financial/audit/document API paths are rejected.

- **Expiry:** At or after the 24-hour deadline, login and session validation fail closed; all remaining sessions are revoked. An authorized administrator must issue a new reset.
- **Migration/backfill:** The additive migration introduces `must_change_password_at_next_login BOOLEAN NOT NULL DEFAULT FALSE` and nullable `password_change_required_until_utc`; existing users remain unchanged. ### ADR-0013 — Session Idle Lock, Configurable Credential Lifetimes, Voluntary Rotation (20 November 2026)

- **Context:** The 2026-11-20 review (AUD-03, R2-01, R2-02, R2-03) found that a session stayed valid for a fixed 12 hours with no idle lock even though `LastSeenAtUtc` was already maintained; that the temporary-password deadline was hardcoded to 24 hours; that console recovery silently invalidated the just-issued password after that deadline; and that the change-password endpoint rejected accounts outside the forced-rotation state, so users could not rotate their own credentials at all.
- **Decision:** Session validity is now the conjunction of three server-side rules: not revoked, before the absolute expiry, and last activity within the idle timeout. An idle timeout revokes the specific session and writes an `AUTH_SESSION_IDLE_EXPIRED` audit event. All three timings (`Security:SessionAbsoluteLifetimeHours`, `Security:SessionIdleTimeoutMinutes`, `Security:SessionTouchIntervalMinutes`) are configuration values clamped at composition time; an inconsistent combination fails at startup rather than silently disabling the lock.
- **Credential lifetime:** `Security:TemporaryPasswordLifetimeHours` (1–168 hours, default 24) sets the deadline for administrator-issued passwords. The domain refuses lifetimes outside that range. Values are passed explicitly by the services; the domain constant remains the default for callers that do not supply one.
- **Voluntary rotation:** Any authenticated, active user may replace their password after proving the current one. The same policy, reuse check, lockout accounting, `SecurityStamp` rotation and full session revocation apply as in the forced path. The forced path remains distinct only in that it also enforces the deadline and clears the marker.
- **Console recovery:** Local-console reset is root-equivalent access by definition. It rotates the stamp, clears lockout/failed attempts and revocation, and does not impose a hidden deadline; the operator is instructed to rotate the password voluntarily after signing in.
- **Frontend:** The authenticated shell exposes a change-password dialog for every user. On success it returns to the login screen with the existing "password changed" notice. The forced-rotation screen now takes its validation messages from the translation bundle instead of inline bilingual strings.
- **Non-goals:** No password history, no external identity provider, no change to password complexity, RBAC, project scoping, CSRF, cookie flags or audit immutability. No migration: no schema change is involved; `LastSeenAtUtc` already exists.
- **Verification state:** Frontend lint, typecheck, 88 unit tests and production build pass locally. .NET compilation, domain/application tests and PostgreSQL integration are verified only by CI on the pull request; do not mark complete until all three required jobs and the post-merge main run are green.

### ADR-0014 — Encrypted, Offsite, Retained Backups on Linux (20 November 2026)

- **Context:** The 2026-11-20 audit (AUD-01) found that the production backup bundle was plaintext, stored on the same host and filesystem it protects, never pruned, and had no second copy. That combination makes theft, ransomware, or disk loss a total-loss event for organization data, and exposes personal and contractual data on any copied medium.
- **Decision:** The Linux backup job now seals the four-component bundle with its SHA-256 manifest, packs it, encrypts it as CMS enveloped data (`openssl cms -encrypt -aes-256-cbc`) against an X.509 recipient certificate, and publishes `promogest_backup_<timestamp>.tar.gz.cms` plus a SHA-256 sidecar. The ciphertext and sidecar are copied to an independent offsite mount and verified there with `sha256sum -c`. Retention prunes artefacts older than `PROMOGEST_BACKUP_RETENTION_DAYS` (minimum 7) but never below the newest `PROMOGEST_BACKUP_RETENTION_MIN_KEEP` (default 3). The unencrypted bundle directory is removed after a successful publication.
- **Fail-closed policy:** Encryption cannot be disabled without `PROMOGEST_BACKUP_ALLOW_PLAINTEXT=1`, and the job refuses to run without an offsite target unless `PROMOGEST_BACKUP_ALLOW_LOCAL_ONLY=1`. An offsite path on the same filesystem as the primary root is rejected unless explicitly excepted for a documented test/DR scenario. The systemd unit declares `RequiresMountsFor` on the offsite mount so a missing mount stops the job.
- **Key custody:** Only the public recipient certificate exists on the server. The private key is generated and retained on the operator side, kept offline in at least two locations, and never stored with the backups or in the repository. Because the key is absent from the host, the backup job performs only a structural envelope check; decryptability is proven by the restore drill, which now accepts the `.cms` artefact and requires `PROMOGEST_BACKUP_DECRYPT_KEY`.
- **Availability:** The application service is restarted immediately after the snapshot manifest is sealed, before packaging, encryption, offsite copy, and pruning, so those stages no longer extend the maintenance window. A sealed snapshot is never deleted because a later stage failed.
- **Verification-boundary:** CI generates a throwaway recipient key pair, runs the real job with encryption, offsite copy, retention pruning fixtures, and then executes the full PostgreSQL restore drill against the encrypted artefact. A single-byte tamper and a renamed artefact must both fail the sidecar check. No claim of verification is made until all three PR-head jobs and the post-merge `main` run are green.
- **Windows parity (2026-11-20):** `scripts/backup-promogest.ps1` now seals, packages, CMS-envelopes (AES-256-CBC, DER), writes a `sha256sum`-compatible sidecar, copies and verifies an independent offsite target, applies retention, and deletes the plaintext bundle under the same fail-closed policy. `scripts/restore-promogest.ps1` accepts a `.cms`/`.tar.gz` artefact in addition to a materialized bundle directory. `scripts/test-backup-crypto.ps1` proves the certificate rules, encryption round trip, sidecar tampering rejection, retention limits, and artefact materialization in CI. Residual gaps: no cross-platform decrypt drill in CI and no point-in-time recovery (WAL archiving).

### ADR-0018 — Project Commercialization Eligibility and CRM/Reservation Separation (23 November 2026)

- **Status (reconciled 27 November):** Product-owner decision approved 23 November; runtime merged in PR #233/#234/#235 and UI #237. P1-09 is Done / Verified, resolving that acceptance dependency. P1-10 remains In Progress / Pending because the technical acceptance reconciliation identified an atomicity/serialization gap tracked in [#280](https://github.com/younestech31/PROMO-GEST/issues/280), not because the user must provide a separate test device or institutional signature. `ProjectCommercializationPolicy` allow-lists only `Commercialization`; the service checks it server-side before modifying hold/unit state, with `409 PROJECT_NOT_COMMERCIALIZABLE` and a denial audit for other project states. This sequential guard is not proof of ordering against a concurrent project-status change. [Seven-criterion acceptance mapping, real-browser results and reviewed images](P1-10-BROWSER-ACCEPTANCE.md).
- **Context:** The current domain distinguishes `ProjectStatus` (`Planning`, `UnderConstruction`, `Commercialization`, `Delivered`, `Suspended`), project-scoped CRM status (`Prospect`, `Qualified`, `Customer`, `Archived`), and an internal reservation (`Active`, `Cancelled`, `Expired`). The current reservation creation service checks unit `AvailableForSale` and rejects archived customers, but the inspected implementation does not check the owning project's commercialization status. The current reservation is an operational hold only, not a statutory contract or cash receipt.
- **Decision:** Marketing and internal reservation creation are allowed only while the project is explicitly in `Commercialization`. `Planning`, `UnderConstruction`, `Delivered`, `Suspended`, undefined values, and any future status not explicitly allow-listed are denied by default. The property unit must independently be `AvailableForSale` and the customer relationship must not be `Archived`. The project-level gate is server-enforced in Domain/Application across every relevant API operation; UI visibility is not an authorization or business-rule boundary.
- **Suspension handling:** Moving a project to `Suspended` blocks new reservations immediately. Existing active reservations are not auto-cancelled, expired, or legally altered. They must be surfaced/marked for an auditable review workflow; until an authorized, reasoned decision is made, the reservation and unit allocation are preserved. The implementation must define a durable review marker/status and concurrency-safe bulk transition without silently releasing units. **Implementation note (PR #233):** the marker is written, not merely required — `ProjectService.UpdateAsync` records one append-only `PROJECT_RESERVATION_SUSPENSION_REVIEW_REQUIRED` audit entry per real transition into `Suspended`, listing the `activeReservationIds` and their count, while changing no reservation state. **Implementation note (P1-10 review queue, merged in PR #235 with the operator UI merged in PR #237):** the durable marker is now paired with a queryable, server-filtered queue. At the PR #279 baseline active holds received `review_required_at_utc` in a second save after the project/status audit save. **27 November acceptance correction ([#280](https://github.com/younestech31/PROMO-GEST/issues/280)):** the previous same-transaction description was incorrect. PR #281 stages status/markers/audits for one SaveChanges and includes the tracked project-root CAS in hold creation. A stale concurrent operation returns 409 with no partial writes; reload and explicit retry are required, including conservative conflicts between different-unit creates in the same project. [Deterministic PG18 tests and current execution verdicts](P1-10-ATOMIC-SUSPENSION.md) are required before closure. Sequential browser acceptance does not prove either property. `GET .../reservations?reviewRequired=true` returns only holds awaiting review, and `POST .../reservations/{reservationId}/review` records `review_completed_at_utc` plus an append-only `PROJECT_RESERVATION_REVIEW_COMPLETED` audit record naming the reviewer. Recording a review is bookkeeping, not approval: status, unit, expiry, and project suspension are untouched, and new reservations stay blocked until an explicit decision changes the project state. The Module E reservations screen surfaces that queue with an explicit Arabic/French notice restating the same rule, and the local Vite preview middleware mirrors the filter and the review endpoint without touching real data.
- **CRM/legal separation:** `ProjectCustomerStatus.Customer` means only that the project-scoped CRM relationship has reached the Customer stage. It is not evidence of a statutory reservation contract, VSP contract, notarial deed, completed sale, or payment. Neither `Customer` nor an internal hold may create contracts, instalments, treasury entries, or accounting postings. Those remain in their roadmap phases and require the appropriate practitioner review.
- **Implementation guardrails:** Inspect and preserve current project membership, permission, project-scope, concurrency, immutable-audit, and PostgreSQL integrity controls. Add Domain/Application and real PostgreSQL 18 tests for the allow-list, all denied statuses, suspension review, no automatic cancellation/release, concurrency/idempotency, and cross-project isolation. Update `DOMAIN-MODEL.md`, `MASTER-ROADMAP.md`, and traceability in the implementation PR. No production data mutation is authorized by this ADR.
